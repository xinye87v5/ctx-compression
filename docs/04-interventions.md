# 04 · 我们改了什么

> 按「**每一轮改动的依据是什么、效果多大**」组织，不按时间顺序。数字带条件与样本量，没出处的不写。
> 断言状态与引用规则见 `docs/05-claims.md`；「压缩何时发生、代价多大、基线保真度多低」见 `docs/03-findings.md`。

**一段话**：我们改了三样东西。① **提示词**：官方指令对自己写下的 KPI（"逐字引用用户原话"）只做到 13.9%，我们迭代七轮才把它抬到显著更好，而每一轮的收益都有限；② **结构性保留**（最重要的干预）：把"用户说过什么 + 它在回应什么"从提示词请求改成 **harness 用代码注入**，主指标从 **≈0% 到 78–100%**，且三次读数**完全相同**；③ **工具足迹**：同样交给代码生成 —— 因为实测证明**即使摘要模型看得到工具结果，路径类锚点也只活 34%**。贯穿的教训：**凡是要害信息，交给代码保证。**

## 一、压缩指令的迭代

起点：官方指令**自己明文写了**我们要测的那两条要求（"在措辞要紧处逐字引用用户目标"、"忠实保留用户反馈尤其是纠正"）⇒ "设计意图类 0/10 逐字存活"不是我们加的标准，是**它自己写下的设计要求没达到**。第一个 A/B 因此只做一件事：**同一份输入，只换最后那条指令**（provider / model / 工具全同）。

### 1.1 逐轮记录：改了什么 → 依据哪个数字 → 效果多大

| 轮 | 改了什么 | 依据（实测数字） | 效果（n 与条件） |
|---|---|---|---|
| 1 | 加 `BUDGET PRIORITY` 四层优先级；新增 `User Constraints, Corrections, and Rationale`（**无条件逐字**）；路径优先不贴代码；合并重复错误；新增 `Transient State` | 官方把"逐字"写成条件式（`where the exact wording matters`）⇒ 设计意图类 **0/10**；`Files and Code` 占篇幅 **30.2%**；同一错误串被保留 **3 份** | 严格 **8.8% → 31.6%**、宽松 21.1% → 50.9%，输出反而短 17%（n=57 条真实发言，**每臂仅 1 次**） |
| 2 | 继续"补规则"：v1（3,517 字）、v2（4,943 字） | — | ❌ 均 lcs/len **0.818（官方）→ 0.675 → 0.566**，单调变差；"v1 优于 v2"配对下**不复现**（p=0.5089） |
| 3 | v3s 写 "completeness outranks brevity"；v3a 改为官方 + 三处手术（语言/逐字/锚点） | <作品>是中文会话，官方那句 `concise English engineering prose` 与任务相悖 | ❌ v3s 输出 8,174 token 撞 8,192 顶，**2/3 次整次拒收**；v3a 23/9/23 —— 加对的内容不必然变差，但**不稳定** |
| 4 | v4：整段覆盖规则 + 输出预算 | 所有臂都保得住"最近一段"，差别全在**向前够多远**；窗口前 1/3 占用户字符 **55%**（1,161/2,117） | 21/20/20/23（区间收紧，但中位仍=官方） |
| 5 | v5：第一节改**编号 + 逐条 + 每条一段 ≥20 字符逐字引文**，禁止合并/按主题分组/转述 | 第一节 ≥20 字引文条数与严格存活 **ρ=+0.931**；官方最差那次按主题重排 ⇒ 覆盖 **19.7%**，逐条引用则 84–100% | 效率首次显著（每千字 p=0.0063），但覆盖率均值差 **+17.8pp 未达显著**（p=0.119，n=7 vs 5） |
| 6 | v6/v7：编号总数自检；把输出预算写清（"目标 ~7,000"；此前写 "roughly 6,000 tokens" 让模型写一半就停） | 我们自己写坏的措辞（3,476 token ⇒ 覆盖 70%） | 下限抬到 **74.1%**、覆盖首次显著（p=0.0105）；⚠️ **但换掉了分钟/行号** |
| 7 | **v8**：加**技术锚点配额**（路径 / 行号 L### / 时刻与时长 / 被推翻的裁定与禁区） | v7 的锚点流失（分钟 5.6 vs 8.2、行号 22.9 vs 31.2） | 覆盖 **p=0.0238**、lcs/len **p=0.0346**、效率 **p=0.0411**；行号反升到 61.5 |
| 8 | **v9′**（4,422 字）：**取消"由模型逐条枚举"**，把预算让给技术内容 | 用户回合改由 harness 保证（见 §二），提示词不必再承担 | 配合 A′ 通过匹配设计；⚠️ 首版措辞 "in as much verbatim detail as you can carry" 又撞顶 1 次，改 BRIEF 后消失 |

**v5 那一行值得抄下来**：4 次重复时效率 p=0.064，**补到 7 次后变差**（p=0.119）—— 补样本让结论变弱，正是它该做的事。

### 1.2 v8 的最终效果（同前缀匹配设计，两窗口）

| 指标 | 官方 | v8 | 精确置换 p |
|---|---|---|---|
| 逐字覆盖（<作品>45 条发言，严格分母 25） | 67.4% [19.7–84.2]，n=5 | **87.9% [79.2–100.0]**，n=6 | **0.0238** ✅ |
| 均 lcs/len · 每千字严格命中 | 0.740 · 1.784 | **0.9266 · 2.691** | **0.0346** · **0.0411** ✅ |
| 逐字覆盖（跨项目 30 条发言，分母仅 5） | 12.6% [8.4–14.8]，n=3 | **17.1% [15.9–17.8]**，n=3 | 区间**完全分离** |

v8 的最低一次（79.2%）高于官方中位（76.5%）；可靠性**9/9 成功、0 撞顶被拒、0 崩塌**，官方在同一对前缀上有 **1 次崩塌**与 **3 次撞顶被整次拒收**。**"严格存活条数"没达显著是仪器的天花板**：官方未崩塌的四次是 20/20/23/24、v8 是 21/21/23/23/24/25，两者几乎重合 —— 差别在**部分保住**那一段。

### 1.3 一个必须先说的反面事实：这条规则是"对着度量写的"

v8 的核心就是"编号逐条引用用户原话"，而度量量的正是"用户原话保住了多少" —— 我们不掩饰。可以这样写的理由是：本项目目标**本来就是保住用户原话**，而原则 P4 规定"模型分辨不出什么文本更有价值"，所以只能用**机械、可核对**的要求替代"提醒它重视"。代价是**收益只在中游指标上成立**：下游效果（压缩后 agent 是否真少犯错）**仍未测**。

## 二、回合级保留（本项目最重要的干预）

### 2.1 缺陷：短发言的"所指"完全不留痕

回指式发言（"同意"、"可以"这类 ≤12 字符的确认/指令）在本项目会话里占 **30%**，短发言整体占 **60%**；而**现行逐字覆盖指标对它们完全失明** —— 抄下"同意"两个字就能拿满分，**保住了"同意"，却不知道同意了什么**。我们为此补了指标 **"所指有痕"**（对上一条助手回复末 2,000 字符的 12-gram 命中率 ≥10%）：它在 3 窗口 × 4 臂共 12 个组合里**几乎恒为 0**，而这些短发言**自身**的逐字存活率是 13–100% ⇒ **提示词路线在这里没有办法**：v8 已是最优提示词方案，它的所指有痕是 **0% ×3**（完整测量见 `docs/03-findings.md` §4.2–§4.3）。

### 2.2 为什么必须动输出侧，而不是再写一条提示词

对照同类系统（不点名）：**有系统是用代码、而不是提示词，来保留用户消息的** —— 与我们的核心发现独立收敛。

### 2.3 实现：harness 注入一份"回合索引"

由 harness 从 `options.messages`（正在被压缩的**面**）机械计算，**不含模型判断**：

```
## Turn Index (harness-generated, verbatim user turns)
- [t1] 用户："…（该回合用户发言的逐字原文，不截断）"
       ← 上文：…（该回合之前最近一次工具调用的 name + 主参数）
- [t2] 用户："…（例：一条 ≤12 字符的确认式发言，照样逐字保留）"
       ← 上文：…（该回合之前助手回复的结尾 250 字符）
```

（示例里的 `…` 是占位符：真实附录里放的是**逐字原文与真实锚点**，发布集不含任何会话内容。）

- **用户发言**：逐字、不截断；排除压缩指令本身、旧 checkpoint（`source.kind === 'plugin'`）、系统注记；
- **所指锚**：取该发言**之前**最近的 assistant 回合，机械抽两样 —— 工具调用的 `name` + 主参数（路径/命令前 60 字符），以及文本输出的**结尾**（250 字符，第二轮改 300）；
- **预算**：超限时保留最近 N 个回合完整、更早的压成一行计数，省略是**可见的**，不是静默丢弃；
- **失败策略**：任何异常**原样透传流**并写存证（`turn-index-error`）—— **绝不留静默 catch**；
- **作用域**：只在 `purpose === 'compaction'` 时生效，其余调用原样透传。

### 2.4 效果：主指标 ≈0% → 78–100%，而且**三次完全相同**

| 指标 | 官方（3 次） | v8（3 次） | **A′（3 次）** |
|---|---|---|---|
| **DEP（回指型）所指有痕** | **0 / 0 / 0%** | **0 / 0 / 0%** | **78 / 78 / 78%**（跨项目窗口 **100% ×3**） |
| DEP 自身存活 | 61 / 74 / 52% | 65 / 83 / 70% | **100% ×3** |
| SELF（自足型）逐字覆盖 | 45.9 / 50.6 / 34.7% | 60.1 / 69.4 / 67.7% | **100.0% ×3** |
| 严格存活条数 | 14 / 14 / 9 | 20 / 22 / 22 | **36 / 36 / 36** |
| 记忆要素（5 项） | — | 基线 | **0 项更低、4 项更高、1 项持平** |
| 可靠性 | 1 次崩塌 + 3 次撞顶被拒 | — | **6/6 成功、0 撞顶、0 退化跨度** |

**关键性质不是"均值更高"，而是"要害部分不再靠运气"**：A′ 三次的逐字类数字**一模一样**（用户回合由代码生成），v8 同一批数字逐次跳动（覆盖 61.1 → 71.9 → 68.6%）。

### 2.5 测量升级时暴露的两个坑（判据都一字未改）

1. 第一版锚取上一条 assistant 消息的**开头**第一句，而指标比的是**末 2,000 字符** ⇒ 指标读 0%。从对话结构看，"用户在回应什么"本来就是对方**结尾的结论** ⇒ **改实现，不改判据**。
2. 第一轮主指标只有 **39%**，未达预声明的 60%。我们没有改判据，而是定位原因：附录预算里 88 行用户正文本身占约 3,950 字符，剩下的只够给 23 条短发言中的 **13 条**配锚 ⇒ 上限本就是 13/23 ≈ 57%。**重配预算**（7,500 → 12,000 字符、锚 250 → 300）后主指标 **78%**。**"未通过"那一轮原样留在归档里。**

### 2.6 生产首验：在未挑选的真实数据上

上线后第一次真实压缩（遮蔽 **574,647 token**、注入 26 个回合、`omitted` 0、一次成功无重试）：所指有痕 **8/8 = 100%**、短发言自身存活 8/8、助手内容 15/15、助手逐字覆盖 **100.0%**。分量更重的原因是：该会话正是**最难样本**（30% 发言为回指式）⇒ "是不是我挑的前缀恰好适合这个方法"这个解释可以放下了。代价：

| 项 | 量级 | 说明 |
|---|---|---|
| checkpoint 变大 | v8 ~10k 字符 → A′ ~19–24k 字符 | 附录本身 ~11.4–11.8k 字符（约 3.4k token） |
| 窗口占用 | 约 **+3.4k token/轮**，直到下次压缩 | 每次压缩取代 350k–570k token ⇒ 占比 **~2%** |
| "每千字效率"变差（1.5–1.7 vs 2.0–3.1） | **是度量假象** | 该口径奖励"少写"，而结构保证的价值恰在"必写" |

## 三、工具足迹：同一套逻辑，"动过什么"也必须由代码生成

**依据**：先量了裁剪（pruning）的代价，结论是**裁剪不是问题** —— 223/223 次裁剪紧贴压缩触发、被裁 seq **100% 落在本次压缩的 `shadowedRange` 内**（越界 0），唯一真代价是"裁了但压缩失败"：2 条 / 5,431 token = **1.79%**。**但同一份工作量出了真问题**：

| 锚点类型 | 摘要模型**看得到**工具结果时的存活率 |
|---|---|
| 路径类（`read` + `grep`） | **34.0%**（n=829） |
| **bash 命令** | **3.1%** |

⇒ 即使把工具结果原样喂给摘要器，**"动过哪些命令"基本必丢**：正确做法是把这份信息**从摘要器的职责里拿走**。实现上就是在 A′ 的**同一注入点**再加一节**代码生成**的内容，来源只有被压缩面里的 `tool-call` 块（**不解析工具结果**）。隔离环境验证：`footprintChars 1,630 / files 19 / commands 25 / omitted 0`、回合索引无回归（72 回合 / 11,384 字符）、压缩成功、**`outputTokens 4,714 / maxTokens 16,384`（28.8%）** ⇒ 附录是代码注入的 text-delta、**不经过模型生成** ⇒ **不吃输出预算、不增加撞顶风险**。

**抽取器被真实数据打了三次脸**（"看着对"和"它对"是两件事）：① `cd×503`（真实命令写作 `cd X && 真命令`，抽取器把 `cd` 当命令）；② 40+ 条**代码碎片**被当命令（在**引号内部**的 `;` / `|` 上切段）；③ 循环**走进了 heredoc 体**，把 `ed = json.load(...)` 识别成命令 `ed`。⇒ 上线判据里专门有一条：**人工核对 20 条**，被接受的文件/命令里**不得出现代码碎片或斜杠列表**。

## 四、输出上限：实测只是"可靠性旋钮"，不是"质量旋钮"

引擎默认摘要上限 `maxTokens = 8192`，而 provider 允许 256k、窗口 1M ⇒ **8,192 是引擎自设的，不是模型限制**；官方臂实测最高已到 **7,521（92%）**，我们已付过 **4 次整次拒收**的代价。预声明的**唯一变量**就是它：

| 臂 | preset | 事件里的 `maxTokens` | 输出 token | 占上限 |
|---|---|---|---|---|
| A | `standard` | **8,192** | 8,138 | **99.3%** |
| B | `ctx20k` | **20,000** ✅ | 7,298 | 36% |

**结果：保真度指标完全相同** —— 逐字覆盖 **100.0% vs 100.0%**、严格 **36/88 vs 36/88**、所指有痕 **39% vs 39%**、自身存活均 100% ⇒ 预测成立：**抬上限买到的是"不再被拒"，不是"写得更好"**。可靠性这侧的论据很硬：旧上限下同一条指令收在 **99.3%**，差一段就整次作废（历史不变、压力继续爬）。

**取值怎么定**（这条纠正来自一次很好的追问：为什么输出上限选 20000 这种非 2 的幂）：技术上 20,000 没有错（值直接作为 `max_tokens` 发出，无对齐要求），**但"没有错"不等于"有理由"**。区间由两端夹住 —— **下界**要明显高于模型自然写出的量（实测成功样本 3.5k–8.1k token ⇒ **8,192 落在自然区间内部**）；**上界**仍要保住兜底意义。⇒ 取 **16,384 = 2× 旧默认 ≈ 2× 自然上限**。

## 五、被后续工作修正的结论（写出来，不美化）

| 我们曾经的说法 | 现在的状态 |
|---|---|
| "压缩指令优化已上线生效" | ❌ 当时**从未生效** —— 一行悬空变量引用被 `catch` 静默吞掉，第一次改写总是回退官方指令；修复并加集成测试（含反证）后才复现 |
| "改进版在**生产上**复现（26.1% → 41.7%）" | ❌ 基线是静默回退成官方指令的产物，处理是 fork 子会话的手动压缩 —— 触发路径、会话、指令三者同时不同；同前缀匹配下方向**相反** |
| "v1 明显优于 v2（44.4% vs 26.7%）" | ❌ 配对设计下**不复现**（p=0.5089） |
| "v5 已确定超过官方" | ⚠️ 只能说**效率上已超越**（每千字 p=0.0063）；绝对保真度的均值差（+17.8pp）**不显著**（p=0.119） |
| "时间/行号锚点不加配额也保得住" | ❌ v7 实测把**分钟**（5.6 vs 8.2）与**行号**（22.9 vs 31.2）换掉了 ⇒ v8 加技术锚点配额才补回 |
| "checkpoint 体积有一个上限旋钮" | ❌ **上限不含附录**：最终 checkpoint ≈ 上限 + 附录。真正的旋钮是**两个预算之和**（回合索引 ≤12,000 + 足迹 ≤4,000 字符） |
| "证据不支持这是探针插件的 bug" | ❌ 就是它的 bug（两处：waterfall 契约、服务取值时机）⇒ 见 `docs/06-toolchain.md` §四的挂载事故 |
| "90 万事件零异常 ⇒ 插件无害" | ❌ 那次重放里用了**假 meter**，恰好替换掉了唯一有风险的依赖 |

**仍然没证明的事（引用时必须带上）**：① **下游效果仍未测** —— 本文所有"更好"只指**用户原话保真**；② 样本量小（v8 是 6 vs 5、3 vs 3，A′ 匹配设计 3 vs 3）；③ A′ 的证据来自 fork 子会话，**未经真实生产流量验证**，生产首验仍是 n=1；④ 两个留出窗口都已"被看过"一次，**不再是全新窗口**。
