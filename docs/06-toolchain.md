# 06 · 工具链：怎样在自己的语料上搭一套压缩测量装置

> 本文是**搭建设计**，不是脚本清单：讲职责怎么划分、判据怎么定、哪些坑必须提前绕开。
> 每个部件都按**角色**描述 —— 用你自己的语言、框架、harness 实现即可，不必与我们的实现同构。
> 数字与结论见 `docs/03-findings.md`；测量口径见 `docs/02-methodology.md`；教训清单见 `docs/07-pitfalls.md`。

**一段话**：直接问"压缩到底有没有代价"是问不出答案的 —— 引擎把压缩做成一个事务，
事务**不带当刻上下文压力**，压力**历史只留末态**，而"改进指令有没有被用上"**在日志里查不到**。
所以装置要补这三个洞，分成**观测**（只读采样）、**干预**（在压缩接缝上改指令与注入附录）、
**分析**（离线复算）三块，且三块**必须能各自独立失败并留下痕迹**。

## 一、三件套的职责划分

| 块 | 职责与关键约束 | 失败时应该看到什么 |
|---|---|---|
| **观测** | 每步之前采样上下文压力，落盘成逐轮序列；捕获压缩事务三态。**严格只读**：不注册工具、不改上下文、不阻断会话 | 一条 `null` 读数，而不是 0，也不是沉默 |
| **干预** | 在压缩接缝上替换指令、注入代码生成的附录。只在**压缩那一次调用**上生效，不影响其它调用 | 每次改写一条存证（改了多少字符、用了哪版模板） |
| **分析** | 离线读落盘产物，复算历史压力、代价、保真度。不依赖被测进程，可重跑、可对账 | 退出码 + 与官方解码器 / 计数器的对账结果 |

两条硬理由：**观测与干预不能合并** —— 观测的产物是你下判断的证据，一旦它和"改造"挤在同一个进程、
同一份状态里，你就是在用被告的证词判案；分开之后，观测块还能在干预回退时继续工作。
**分析必须离线** —— 在线算指标会把口径藏进代码路径（改口径要重启），并让"样本"只是"这一次运行"；
它的验收条件是**能和上游自己的解码器 / 计数器对上**。观测块至少记三类事件，字段名随意但语义固定：

```jsonc
// 逐轮采样：每步一行，带会话、压力 token、日志修订号
{"kind":"step-pressure","session":"…","pressureTokens":512345,"logRevision":4242}
// ★ 缺口 1：压缩事务本身不带当刻压力 —— 补上，且与引擎自己的触发判断用同一个读数
{"kind":"compaction-start","compactionId":"…","turn":45,"pressureAtStart":{"pressureTokens":743816}}
// ★ 缺口 2：事务前的压力序列（官方只存末态）—— 质量线标定需要它
{"kind":"compaction-end","error":null,"pressureAtStart":{…},"recentSeries":[…]}
```

**只读插件与压缩改造共用的安全约束**（写进代码，不是口头承诺）：不注册工具、不改上下文、
不阻断会话；不替换引擎的压缩服务（与任何压缩后端并存）；不产生模型可见内容；处理器异常必须
**吞掉但落存证**；**压力取不到时降级为 `null` 而不是 `0`** —— 0 会被读成"压力很低"，是会自己长出
结论的假值。

**干预块的契约**：它只该看到"正在被压缩的那一面"（候选消息集合）⇒ 能改指令文本、能附加代码
生成的文本，**改不了**范围选择与保留策略 —— 这条要写进模块头注释。

## 二、两次挂载事故的根因与教训

两次都不是"逻辑写错了"，都是**契约与时机**。

### 2.1 插件契约：配置 schema 写错，整个进程起不来

**现象**：宿主反复重启（计数器爬到二十几次），日志只有一行：
`failed to apply loader entry …: Cannot read properties of undefined (reading 'validate')`。
**根因**：宿主约定"声明配置 schema 时，导出的必须是符合某种标准校验协议的对象"；我们导出了普通对象，
宿主装配时去读那个协议字段 ⇒ 抛错 ⇒ **加载失败拖垮整个进程**。
**修法**：**不导出 schema**，改用带默认值的兜底取值（宿主对没有 schema 的插件跳过校验）。
**教训**：插件里"可选地声明某样东西"往往是**全有或全无** —— 声明了就得完全合规；
上线前必须有"配置能被加载"的判据：`<宿主> --profile <名> --dump-config` 退出码 0 才算可加载。

同一族的第二次：宿主的事件钩子分**观察者**与**瀑布**两类，瀑布钩子的处理器**必须把 `next()` 的
返回值原样传下去**。我们照观察者写、返回了空值 ⇒ 链路值被吞 ⇒ 下游读不存在的字段崩，每回合在
十毫秒内失败。这类故障最难找的地方是**它从不抛错**，日志里什么都没有 —— 那不是"报错"，是
**破坏契约**。修法是给观察者一个统一包装：自己出问题就记一行日志、然后**照常调用 `next()`**
（语义是"我无意见"）；`next()` 抛错则**原样上抛**（不该替别人掩盖故障）。

### 2.2 服务异步装载：不能只探一次

**现象**：插件**挂载成功、回合正常、零报错**，但探针**一条压力记录都没有**。
**根因**：装配函数是**同步**的，加载器却**异步**逐插件挂载 ⇒ 装配阶段探测某个服务得到"还没有"，
而那个失败结果被**永久缓存**。实测同一次运行：装配阶段读数 `null`、运行阶段同一个服务读数是 8,366。
**修法**：**惰性解析 —— 每次用前取，成功一次后缓存，失败不缓存**；一次瞬时缺席不能让插件永久残废。
同一缺陷在干预块上线后又复现一次（无界面会话里相关服务尚未装配，探测一次失败后再也不试），
于是改成**可重试挂载**：首次失败写 `mount-deferred`，随后每 250ms 重试、最多 60 次（约 15 秒），
成功写 `mounted-late{tries}`，打标防重复包装，装配函数本身**绝不抛**。
另两个伴生坑：**`typeof null === 'object'`**（追踪语句打印"拿到了对象"，这个**假绿信号**让我们白转
一轮）与新用例第一次写成**恒真判据**（断言"那个方法是函数"，而那个值**就是测试自己赋的**，
**因为反证没有变红才被发现**，见 `docs/07-pitfalls.md`）。

**安装纪律**：**改完必须重启才生效** ⇒ 第一次挂载用**独立端口 + 独立 profile**，崩溃只影响那个
实例；不在被观测的会话里自杀式重启。另外，还有一条尚未解释的观测：我们见过"改了配置但没重启，
旧进程也记了 mounted"，与更早的"不改不生效"矛盾 ⇒ **别把"没重启"当成"一定没生效"，以存证为准。**

### 2.3 挂载成功 ≠ 功能生效

**现象**：改进版指令"上线"了一整天，**一次都没用上** —— 当时**全部验证都通过**，这才是真问题。
**怎么发现的**：用**产物**当判据，而不是状态。官方模板产出的 8 个固定章节 ⇒ 摘要里**全部命中**；
改进版独有的两个章节 ⇒ **一个都没有**；改写存证 ⇒ **0 条**。
**根因**：一行**悬空变量引用**（把局部变量抽进纯函数后，外层仍引用旧名字）触发运行时错误，
被 `catch` 静默吞掉 ⇒ **静默回退官方指令**；它只发生在"第一次改写"这条分支上，而生产挂载后
恰好只压缩过一次，正中该分支。
**掩盖它的四件事，每件都该抄进检查表**：`catch` 只写日志**不落存证**；单元测试只覆盖**纯函数**、
碰不到装配作用域；挂载存证与预检证明的是"**挂上了**"；回退路径的设计没错，**错在回退不留痕**。
**修法**：用返回值替代外部名字；**`catch` 必须落存证**（含 message 与栈）；删掉会说谎的判据
（用身份比较判断"补丁是否生效"，在包装 / 代理下恒为 false）；新增**集成测试**直接驱动装配产物，
并做反证（把缺陷放回去，用例立即变红）。

> **三条可迁移的结论**：① **读契约 → 写实现 → 按契约写测试**（正确顺序，我们反了）；
> ② **回退可以，静默不行**；③ 必须有"**功能真的发生了**"的端到端证据。

## 三、一条命令自检

把下面四段串成**一个入口脚本**（`./selfcheck.sh` 之类），**退出码 0 才算通过**：

| 阶段 | 做什么 | 判据 |
|---|---|---|
| 1 | 离线断言套件 | 全部通过；**断言数写进输出**，方便发现"用例被删空" |
| 1b | **上游漂移检测** | 赖以识别的指令文本 / 事件形状还能被认出来；漂移 ⇒ 显式失败，不让干预块静默失效 |
| 2 | **端到端真实回合**（无界面，不需人开浏览器） | 进程退出码 0 + 无框架级错误 + 有读数 |
| 3 | **读数来源核验** | ≥2 条采样、至少一条**非零**、来源字段标明是压力表读数（全零 ⇒ 观测块又没拿到服务） |
| 4 | 契约断言 | 观察者确实原样传递链路值（§2.1 那个"从不抛错"的故障，靠这条挡住） |

```bash
cd <你的装置目录> && ./selfcheck.sh     # 退出码 0 = 全通过；1 = 有检查项失败
```

配套三条测试纪律：**用真实 payload**，不用自造样本；**替身要比现实更严**，尤其在被测依赖的
**时序**上不能更宽松（我们的替身在装配阶段就返回服务，绕过了真实异步时序，于是缺陷漏网）；
**新用例必须做反证** —— 把实现改回缺陷版，确认测试**真的会红**。另：**不要断言模型回复的措辞**，
那测的是模型的用词习惯，不是你的契约。不自检的代价不对称：装置坏了不报警，只会**继续出数**。

## 四、判据先冻结

**预注册脚本必须无参数、无分支、固定种子。** 跑之前把一个文件写死，然后**只跑一次**。
理由不是洁癖：规格可以事后调，你就永远能找到一个显著的结果，而那个 p 值不是证据。
写明就冻的关键条款：不搜最优窗口长度（固定 10 条）；不搜最优切点（用连续变量，不二分）；
不做亚组分析；**不加入探索阶段见过的协变量**（要加就得新开一份预注册）；无论结果如何原样报告，
**不显著就不得再作为结论引用**（口径见 `docs/02-methodology.md`）。判据要落到**可判定的产物**上：

```bash
./your-analysis.js --preregistered            # 无参数入口；种子与阈值写死在文件头
grep -c 'rewrite-applied' reports/*.jsonl     # 判据是"改写发生了 N 次"，不是"插件已挂载"
```

判据写在**看到结果之前**，并且要有**自动化守候**：生产下一次压缩发生时按冻结判据核对并落盘，
而不是等你想起去看；判据与产物要能**按文件名与字段定位**（每个入口、每份产物在一处登记，
一个 `README` 即可），否则三个月后没人记得哪个数是谁写的。

## 五、怎么开始

按这个顺序走，每一步都能独立失败、独立收手：

1. **先测量，再动手。** 目标语料先跑观测块，拿到逐轮压力序列与压缩事务三态；此时**不要**写任何
   干预代码 —— 先把"压缩在多大压力下触发""代价持续多久"这类描述性事实拿到手。
2. **冻结判据。** 写一个无参数、无分支、固定种子的预注册脚本，把成功标准写成可判定的产物
   （哪些章节出现、注入增了多少字符、某指标达到多少）。**在跑之前**写。
3. **小样本验证干预。** 在**独立端口 + 独立 profile** 上挂载干预块，把触发阈值压到极小，
   让"要等几小时才发生一次"的链路在一次运行里发生；同时打开端到端存证。
4. **跑自检。** §三 那条命令必须绿；红了就修工具，不要解释结论。
5. **才改生产。** 上线后按冻结判据守候，**以存证为准**；回退随时可以，但**回退必须留痕**。
   每一步的验收都不是"跑通了"，而是"**我能证明它发生了**"。

## 六、边界与不适用

- **插件拿不到引擎内部状态时怎么办。** 观测 / 干预块只看到接缝上递过来的东西 —— 通常是"正在被
  压缩的那一面"（候选消息集合），而**看不到会话标识、也看不到被遮蔽的区间**。⇒ 凡是要知道
  "被压掉的是哪一段"的改动（把稳定检索入口写进摘要、把裁剪改成按压力触发），**必须改引擎本身**，
  不要用插件硬凑；能凑的替代品是靠产物文本里可判定的特征做归因，并把结论适用范围明确降到
  "**接缝可见的部分**"。
- **上游会漂移。** 赖以识别压缩指令的文本、事件形状、服务名都会变 ⇒ 把"静默失效"变成"显式失败"，
  否则你会在一套已失灵的仪器上继续读数（§三 阶段 1b）。
- **样本量下限。** 逐轮采样只在**挂载之后**的会话可见，历史会话**无法补录** ⇒ 开工越早越好；
  同臂重复的**极差就是效应量的分辨率下限** —— 先量噪声再谈效应；很多结论的 n 只有 2–10，
  那就逐条标注 n，不要用"全库"这种词盖过去。
- **不要在别人的生产服务上试错。** 第一次挂载用独立端口 + 独立 profile；等生产具备"回退留痕 +
  判据守候"之后，再谈上线。**不适用**：这套装置不实现压缩算法、不改摘要模型 —— 它给的是
  **测量方法 + 接缝上的输入/输出注入**；想复现任何结论都需要**你自己的会话语料**，
  而原始会话数据不在公开集里。
