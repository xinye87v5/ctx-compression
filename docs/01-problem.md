# 01 · 问题：压缩为什么难，代价在哪

> 长会话的 agent 每隔一段时间必须压缩历史。这看起来是"摘要写得好不好"的问题，实际上不是。
> 本文给出三条结构性原因、两种代价视角，以及一个被现有机制掩盖的关键区分。
> 实测发现见 `docs/03-findings.md`，本文不重复。

---

## 一、要解决什么问题

上下文压缩是一个**率失真决策**：在预算 `B` 下，保留与丢弃哪些由上下文派生的信息、
以何种保真度保留，才保得住下游任务效用。它的 information-bottleneck 形式是

```
max  I(Z ; Y | Q)      保住"能预测答案"的那些比特
s.t. I(Z , H) ≤ B      预算约束
```

其中 `H` = 模型能拿到的全部历史，`Z` = 压缩后的表示，`Q` = 查询，`Y` = 正确答案。
（形式化取自本项目主文献 Colaco & Lahjouji (2026)，见 `日志 #01` §一。

这不是新问题，而是**四个互不引用的研究社群解的同一个问题**：KV cache 驱逐、prompt 压缩、
有界状态架构、agent 记忆整理。**约束也不是"磁盘不够"** —— 原文一直在磁盘上；
约束是模型的上下文窗口：不压缩任务没法继续，压缩就要在一次前向里决定丢掉什么。

---

## 二、为什么"把历史摘要一下"不够

因为难度不在措辞上，而在三个结构性事实上 —— 三条都不随模型变强而消失。

### 2.1 训练不是"超大上下文"，没有可比的先例

常见类比是"基础知识 = 超大上下文，记忆问题早该成熟了"。它在**容量**上成立，在**机制**上不成立：

| | 训练（写进权重） | 上下文压缩 |
|---|---|---|
| 载体 / 更新 | 参数（固定大小的表示），数十亿次梯度步、全局蒸馏 | token 序列，**一次前向**、局部、单遍 |
| 代价位置 | 一次性、离线 | **在任务关键路径上**，每几十分钟一次 |
| 目标 | 让语料分布可被泛化重建 | 让**这一次**任务能继续 |

训练其实也在解率失真问题，只是用了最昂贵的解法：**用算力换掉率失真**。压缩没有那个算力预算，还必须在关键路径上完成 —— **这是难度差异，不是成熟度差异。**（`日志 #13` §一

### 2.2 那些"成熟好用"的记忆方案，全都不做压缩

| 方案 | 它做什么 | 是否销毁信息 |
|---|---|---|
| 向量数据库 / RAG、文件存储、append-only 日志 | 建索引或落盘，**原文原地保留**，按需读回 | ❌ 不销毁 |
| **摘要式压缩** | **把原文替换为一份失真的转述** | ✅ **销毁** |

前者不是压缩方案，是**"带索引的不销毁"**：不设预算上限、不需要预知查询、没有失真 —— 它回避了整个率失真问题。**真正做压缩的只有最后一行**，而它被迫同时接受三个约束：有限预算、预知查询、接受失真。它**不是"还没做好的 RAG"，是另一个问题。**（`日志 #13` §二

### 2.3 最根本的一条：压缩器的先验方向是反的

摘要器就是后面要用摘要的那个模型，于是它的统计先验决定了它保留什么 —— **而这个取向与信息价值相反**：

```
模型先验强的区域  →  "这句话大概会这么说"  →  改写成更"典型"的版本
模型先验弱的区域  →  "这个我编不出来"      →  只能照抄或丢弃
先验越熟悉的内容越容易被抹平；越有辨识度的内容越容易被磨掉。
```

而**保真度恰恰只在"先验弱"的地方才重要**：

| 内容类型 | 模型先验 | 丢了能否重建 | 保真度要求 |
|---|---|---|---|
| 通用散文 | 强 | ✅ 能写出像样的 | 低 |
| 代码路径 / 文件名、精确数值 / 口径 | 弱 | ❌ 编不出来 | **必须逐字** |
| 用户的判据措辞、长期创作项目的语感 | 弱 / 中 | ⚠️ 只能写出"类似意思"或"统计上合理"的 | **必须逐字**（意思、"合理"都不够） |

> **压缩器最擅长压的，恰好是最不需要保留的；最需要保留的，恰好是它压得最差的。**

不是调参问题：**压缩器按"统计上重不重要"来压，而需要的判据是"丢了之后能不能重建"。**
（`日志 #13` §三、§五

## 三、代价之一：信息论视角 —— 率失真与 query-agnostic

**① 可压缩性由任务决定，不由文本决定。** 定义任务条件信息量 `I*(Q) = I(Y ; H | Q)`，
即"回答 `Q` 真正需要 `H` 的多少比特"，则**可达到的压缩比 ∝ 1 / I*(Q)**：
答案比特数高的任务（精确检索、多跳）压不动，答案低熵的任务（要点提取、冗余散文）压得很好。
这是同一台压缩器"在摘要任务上近无损、在检索任务上崩溃"的原因。（`日志 #01` §2.1

**② 不知道查询，就要付 `H(Q)` 的价。** query-agnostic 算子必须把预算摊到整个查询分布上，
所以它的**有效每查询预算只有 `B − H(Q)`**；query-conditioned 算子则能把全部 `B`
花在与答案相关的比特上。**差距 `H(Q)` 就是"不知道查询"的精确价格** —— 可定价的损失，
不是"感觉变差了"。agent 场景天然 query-agnostic：压缩发生时，下一步问什么还不知道。（§2.2）

**③ 说不清"压缩质量"，是因为没定义失真 `d`。** 率失真函数
`R(D) = min_{p(z|h): E[d(h,z)] ≤ D} I(H ; Z)` 的形状**完全由 `d` 决定**。
领域里常见的重要性启发式（注意力质量、困惑度、模型自己的显著性判断）在此都被读作
**失真的代理估计器**。对代码 `d` 是"标识符是否逐字保留"，对创作是"语感是否一致" ——
**不同的 `d` 给出不同的 `R(D)`，也就给出不同的最优压缩器。**
所以第一步不是挑压缩器，是把 `d` 定义成可测量、可自动采集的形式。（§5.3）

两条硬边界决定了"改进措辞"这条路的天花板：

- **数据处理不等式 `I(Y;Z) ≤ I(Y;H)`**：摘要不会创造信息，只会减少（定理，非经验）。
  想让压缩后的表示"比原文更有用"，只有在**改变了使用方式**时才可能 ——
  把散文变成结构化字段、把长文变成指针。**纯文本摘要做不到。**
- **Fano 下界**：预算低于 `I*(Q)` 时错误率有下界，任何架构都逃不掉。
  能突破的只有三件事：**提高 `B`、获得 `Q`、获得可逆性。**

## 四、代价之二：语言学视角 —— 回指的可及性

**指代形式本身编码可及性。** 可及性理论研究说话人如何用不同形式指代同一实体：
零代词 → 代词 → 指示词 → 短名词短语 → 完整名词短语，编码的是**该实体在听话人心里有多容易被激活**。
既然指代本身就能承载信息，**压缩的正确定性形式就不是"把内容缩写"，而是"把内容替换为一个
足够可及的回指形式"**。这正是"把数十万字的正文压成 `见 <repo>/… 第 3 节`"可行的依据 ——
它是一条回指，不是一个缩写。（`日志 #01` §6.1

**旧信息可以省，新信息不能省。** 话题-述题结构与信息状态（given / new / accessible）表明：
已知信息可以高度压缩甚至省略，新信息必须完整表达。所以该判断的不是"说了什么"，
而是**"哪些还是新的"**。产物一旦落盘，它就从"新"变成"已知"，从而变得可压 ——
这是"阶段边界 = 压缩时机"的一个独立的语言学解释。（§6.2）

**省略要合法，前提是共同背景存在。** 话语的预设必须落在双方的共同背景里，否则无法理解。**没有蓝图时压缩是危险的，因为省略掉的内容无法被重建；有蓝图时省略是合法的，因为接收方（后续的自己）可以通过蓝图把省略部分找回来。** 语用学上也不存在"绝对重要"的内容，只有"相对于当前目的重要"的内容 —— 与信息论一致：**压缩策略必须条件化在目的上。**（§6.3、§6.4）

## 五、为什么不可逆，以及它如何改变设计取向

压缩器是"有损且单向"的：它把一段 token 序列换成另一段更短的序列。

**关键事实是：原文还在磁盘上，但模型再也看不到它。** 这个差异是可测的：
19 次压缩事务、**213,964 tokens** 的模型可见历史被摘要取代，全部不可逆；
而全部 13,740 次工具调用里，**召回类调用为 0 次** —— 没有召回通道，也就没有补救。
（`日志 #03`

从"不可逆"出发，四条设计取向不是偏好，而是被迫的：

1. **可逆性是第一等的，且优先于任何打分技巧。** 同一预算下，能取回被丢弃内容的方法胜过不能取回的，而且它赢的正是那些**取决于被丢弃材料**的查询。既然不可重建的内容一旦被压就永久损失，**可逆性就不只是"减少损失"，它是唯一的补救通道。**
2. **压缩的目标物是指针，而不是缩写** —— 让你知道**去哪找**，而不是替代**找到的东西**。
3. **可逆性是一切测量的前提**：没有召回通道，连"这次压缩丢了什么"都无法事后核对。
4. **不可逆放大了压错位置的代价**：可逆系统里"压多了"是可修的，不可逆系统里它是终局的。

## 六、工作台型历史 vs 进度型历史

把上面几条合起来，得到一个被现有机制完全掩盖的区分：

| | **工作台型历史** | **进度型历史** |
|---|---|---|
| 上下文是 | **工作台本身** | **进度指针** |
| 内容性质 | 决定是怎么做出的、依据是什么 | 已经做完的事，结论在磁盘上 |
| 丢一段的后果 | 信息没了，要重新抠一遍 | 无所谓，磁盘上有 |
| 该不该压 | **不该** | **该，而且可以很激进** |
| 判据 | 丢了能否重建 | 丢了能否从磁盘重读 |

用信息论的语言，这就是 `I*(Q)` 的高低：**"上下文是工作台"意味着答案比特就在上下文里；
"上下文是进度"意味着答案比特在磁盘上，上下文只是索引。**
语言学上对应"新信息 vs 已知信息"，也对应"共同背景在不在"。

**而现有机制对这两种情况的处理完全相同** —— 它只看一个标量：token 压力。

## 七、核心命题

> **压缩的第一性决策不是"保留多少"，而是"这段历史是工作台还是进度"。**

形式上，这等价于用**任务条件信息量 `I*(Q)` 替代固定阈值**：阈值只看"还剩多少空间"，
不看"接下来要问什么"；而 `I*(Q)` 看的正是后者。麻烦在于压缩时刻还不知道 `Q` ——
但我们不需要 `Q` 本身，只需要它的一个**廉价代理**：**当前处于哪个阶段、这一阶段的产物是什么。**
阶段是分布式的（这一阶段在做什么、还剩多少），比点状的 `Q` 更容易获得，
足以把预算分配到正确的比特上。**本项目占据的位置就是**：用任务结构（蓝图 / 阶段）
作为 `Q` 的替代条件，实现 query-conditioning 而不必预知查询。

另一侧得到印证：「价值」不是文本的属性，而是文本与任务的关系（同一个量 `I(Y ; x | Q)`）。
所以它在文档里根本不存在，事后也无从计算 —— 检索器和压缩器都只能用廉价代理，
而两个代理都不好。**这就是"检索和压缩同时都不好用"不是巧合的原因。**
（`日志 #14` §二

---

## 八、结论

> **压缩不难在"写得短"，难在它必须在不知道问题的时刻，决定哪些比特以后再也拿不回来。**
>
> 而这件事唯一能做好的前提，是先分清这段历史是**工作台**还是**进度**：
> 对进度可以激进压缩；对工作台，正确的动作是**根本不压**，或者把它变成指针加召回通道。
