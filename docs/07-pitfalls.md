# 07 · 踩过的坑：七条可迁移的教训

> 本文写给**做 AI agent 与评测、但没读过本项目其他文档**的工程师。
> 每条按四段写：**现象 → 为什么错 → 怎么发现的 → 以后怎么避免**。
> 七条全部来自我们自己的事故与返工，不是推测；出处指向归档日志的原始记录。

**一段话**：这七条有同一个形状 —— **失败发生在"看起来成功"的那一侧**：挂载成功而功能没生效、
断言通过而用例是空的、指标出数而抽取器是坏的、统计全绿而总体被污染。
代价都不在出错的那一刻，而在**结论被写下来之后**：一个没生效的优化会让我们以为方向可行，一个坏掉的分母会让所有下游的显著性与相关性失去意义。

---

## 一、挂载成功 ≠ 功能生效

**现象** 一次压缩指令优化上线后跑了一整天，**一次都没生效** —— 那天的真实压缩用的仍是官方指令。
而当时的验证项全绿：挂载存证有、预检 0 错误、服务健康。同类还有一次：插件声明依赖一个在宿主平面上并不存在的服务，于是它**静默停在 pending**，连一条存证都不写，启动白跑一次。
（原始日志 #36（未随本仓库发布）、原始日志 #37（未随本仓库发布） §二）

**为什么错** 挂载存证、预检、健康检查证明的是"**挂上了**"，不是"**功能发生了**"。三个具体机制：
① **装配是同步的，服务装载是异步的** —— 在装配阶段取一次服务会安静地拿到 `undefined`；若把这个失败结果缓存下来，**一次瞬时缺席就永久残废**；
② **"出错就退回原路径"的 `catch` 只写日志不落盘**，于是"失败了"与"没触发"在证据上无法区分；
③ **用身份比较判断补丁是否生效**（`obj.method === myFn`）在代理/包装下恒为 false，是个**会说谎的判据**。
（原始日志 #23（未随本仓库发布） §7.1–7.2、原始日志 #36（未随本仓库发布） §三）

**怎么发现的** 用**可判定的产物**当判据：那次摘要的章节名里，官方模板的 8 个章节全部命中，改进版独有的 2 个章节一个都没有；而插件自己的改写存证是 **0 条**。
顺着"零存证"查下去，根因是一行悬空变量引用 —— 重构时局部变量被抽进纯函数，外部引用变成未定义并抛错，被 `catch` 吞掉。它**只在"第一次改写"这条分支上发生**，而线上挂载后恰好只压缩过一次，正中该分支。
随后用隔离实例 + 极小触发阈值复现整条链路，仪器读数显示"拦到了调用、判定要改"，但存证缺失 ⇒ 只可能是判定之后、存证之前抛了异常。修复后存证显示 `1802 字符 → 3517 字符`，1802 正是官方指令的确切长度。
（原始日志 #36（未随本仓库发布） §一、§四）

**以后怎么避免** ① 为"功能是否发生"留一条**端到端证据**（改写发生了 N 次、产物带有新指令的独有特征），而不是"挂上了"；
② **回退可以，静默不行**：任何"出错就退回原路径"的 `catch` 必须落盘，带 message 与栈；
③ 可选依赖**惰性解析**：每次用前取、成功缓存、**失败不缓存**，且不要写进必选依赖（那会让不依赖它的功能一起消失）；
④ 把"要等几小时才发生一次"的链路放进隔离实例，把触发阈值压到极小，让它在一次运行里发生。

## 二、反证不变红，说明用例没测到东西

**现象** 为"重试挂载"写的新断言是 `typeof llm.stream === 'function'` —— 而那个值**就是测试自己赋的**，恒真。把实现改回缺陷版去跑反证，测试**没有变红**。
（原始日志 #34（未随本仓库发布） §六）

**为什么错** 恒真的断言不测实现，它测的是测试里写的字面量。表面上"新增断言 + 全绿 = 有覆盖"，实际上**用例是空的**。更普遍地说：反证（把实现改回缺陷版，确认测试会红）失效时，它说明的不是"实现没问题"，而是"**用例没测到东西**"。
同一族还有两个漏洞：mock 在**时序上比现实宽松**（mock 的取值在装配阶段就返回服务，绕过了真实的异步时序，于是缺陷从上百项断言下漏过）；纯函数测试与装配测试之间有一整层空白，而真实事故恰好落在装配作用域里。
（原始日志 #23（未随本仓库发布） §7.4、原始日志 #36（未随本仓库发布） §五）

**怎么发现的** 按"新用例必须做反证"的既定规矩跑了一次：把重试间隔改成一个不可能到达的值，测试照样全绿 —— 才发现用例是空的。改成断言**可观察行为**（附录是否真的被注入文本增量）后，反证立刻变红。修复后的集成测试在缺陷复现时确实失败、修复后全过，我们据此确认它是**有效的，不是安慰剂**。
（原始日志 #36（未随本仓库发布） §三、原始日志 #34（未随本仓库发布） §六）

**以后怎么避免** 新用例必须做反证，并把"**反证不变红**"本身当成一条判据；断言**可观察的产物与副作用**（落盘记录、注入的字节、返回的行为），不断言"我自己赋的值"；mock 不只要在形状上不比现实严格，还要**在被测依赖的时序上不比现实宽松**；代码改动集中在装配层时，补一个驱动真实装配产物的集成测试。

## 三、新指标必须先抽样看它抓到了什么

**现象** 同一个模式在一个项目里**犯了三次**：
① 引文计数按引号字符统计 —— 而那个样本用的是反引号，于是高覆盖（98.7%）的摘要被数出 **0 条**引文；
② 按"这一行里是否包含某字符串"数事件 —— 于是"内容里提到过该字符串"的行也被算进去，得出"**2/68** 个子代理压缩过"这个并不存在的现象，按事件类型精确匹配重数 ⇒ **0/68**；
③ 路径正则 `(?:[\w.-]+\/)+` 会匹配英文散文里的 `A/B` 写法 —— "实体回溯 **60.9%**"的分母里，大半是 `CLI/IDE`、`gh/glab`、`tokens_before/tokens_after` 这类词组。
（原始日志 #34（未随本仓库发布） §六、原始日志 #44（未随本仓库发布） 附 D4）

**为什么错** **三次都不是现象有问题，而是抽取器或分母有问题**。坏掉的指标最危险的地方在于它照常出数、照常"合理"：与预期同向的偏差不会被注意到，而分母一旦被污染，下游的显著性、相关系数、逐条结论全部建立在错的集合上。
（原始日志 #44（未随本仓库发布） 附 D4 第二版）

**怎么发现的** 每次都是"**按规矩抽样看它抓到了什么**"暴露的：数出 0 条时去看了那一条原文（用的是反引号）；看到 2/68 时去看是哪两条（只是内容里提到）；跑出 60.9% 时把"找不到的实体"前 20 个逐条打印出来看（绝大多数根本不是实体）。第三次之后才把它写成硬规矩：**任何新指标在出数之前，先抽样看它抓到了什么。**
（原始日志 #44（未随本仓库发布） 附 D4 第二版与"跨三次事故的共同教训"）

**以后怎么避免** 新指标先人工看 20 条它判正的样本 + 20 条它判负/漏掉的样本，再上量；对"数出 0 / 数出全部"的读数优先怀疑抽取器；抽取器必须配**校准集**（先人工标注 20 条，抽取器在它上面全对，才允许上量）；把抽取器的原始输入与输出样本随结论一起归档，否则事后无法判断这个数字是怎么来的。

## 四、全 0 / 全 1 / 荒谬比例（>100%），先当 bug 查

**现象** 一个新写的体量脚本第一版跑出"**报告比它读到的原文还大**"—— 比例 **350% / 541%**。更早还有一次：某个机械指标全 0，我们一度把它记为发现。
（原始日志 #44（未随本仓库发布） 附 D4 第一版、原始日志 #07（未随本仓库发布））

**为什么错** 这些数在逻辑上不可能或近乎不可能：报告是原文的转述，不可能比原文更大。把它当发现记下来，会直接导向一个错误的结论（"子代理在编造"）。**违反常识的数字是系统在喊"我的实现错了"** —— 它是免费的自检闸门，而跳过它要付的是结论的代价。

**怎么发现的** 顺着荒谬比例反查：工具结果的文本**嵌在更深一层的字段里**，而取值函数只取顶层文本块 ⇒ 每个工具结果都被抽成空，"原文侧"严重漏计；改成递归抽取后，原文侧从 1.8k 字符变成 **449k** 字符。全 0 那次则是在"指标本身在骗人"上第三次栽跟头之后才定下的规矩。
（原始日志 #44（未随本仓库发布） 附 D4 第一版、原始日志 #07（未随本仓库发布））

**以后怎么避免** 把"逻辑上不可能"做成自检闸门：**比例 >100%、恒 0、恒 1、全库计数在去重前后不一致** —— 一律先当 bug 查，再当发现。尤其警惕**分母侧漏计**："只取顶层字段"是这类 bug 的重灾区。闸门要跑在**看结果之前**，而不是在结果被质疑之后。

## 五、污染有两种：数重了 vs 数了不该数的

**现象** 同一份"全库统计"里同时存在两类污染。
**① 数重了**：某次全库统计是 112 个会话 / 73 次压缩事务 / 223 次裁剪；去重后是 **36 个血缘根会话 / 33 次压缩 / 73 次裁剪**，裁剪 token 从 930,205 掉到 **302,945（3.1× 放大）**。
原因是会话 fork 会把父会话的事件**原文拷进种子区**（实测种子长度 1,984,576），于是父会话的每次压缩都在每个子会话里再出现一次；被 fork 最多的一个根被 fork 了 **17 份**。
**② 数了不该数的**：一条本意是"用户反馈"的通道里混进了子代理的**委派提示词** —— 来自子代理会话的信号 **33 条 33/33 全部为负向**，因为只读类任务的委派提示词常写成"不要修改…"。后果是一项"压力与抱怨无关"的分析，其总量里 **84% 是子代理会话**。
（原始日志 #34（未随本仓库发布） §六）

**为什么错** 前者是**同一批真观测被数多次**，去重可解；后者**根本不是"用户反馈的东西"被当成了用户反馈** —— 每条都只出现一次，只是不该在这个通道里，**去重救不了**。两类污染的修法完全不同（一个改口径，一个改总体定义），混为一谈就会把后者当前者处理，于是"已经去重了"变成了虚假的放心。
（原始日志 #34（未随本仓库发布） §六）

**怎么发现的** 放大倍数是先可疑起来的：裁剪 token 的 3.1× 无法用业务变化解释，于是去查会话目录元数据，发现大量会话带父会话指针（66 个子代理 + 10 个 fork）⇒ 随后建了**血缘识别 + 事件级去重**的口径，并把"两种去重规则必须给出相同结果"作为验收条件。第二类是复核时**按会话来源把总量拆开**才看到的。
（原始日志 #34（未随本仓库发布） §六）

**以后怎么避免** 任何"用户行为 / 用户反馈"类指标，开工前先问一句：**这条通道里混进了谁？** 并**先按来源拆一遍总量**，看每类各自贡献了什么；说"全库 N"之前必须过血缘识别 + 事件级去重，并写清单位是**事件**还是会话（语料的单位是事件）；分析产物与实验产物要有办法从总量里剔出去。

## 六、频率启发式只能当否决权，不能当许可证

**现象** 把一条"上级目录同名频率"的启发式实现成**接受**规则（"某一段在前文出现过 >1 次就放行"）后，`12.5/88/3x`、`AA/BB/CC`、`XX/YY/ZZ`、`31.4/207.55/48.9` 这类**用斜杠分隔的评分与缩写列表**全部被放行 —— 而自动自检 **8/8 通过**。
（原始日志 #34（未随本仓库发布） §六）

**为什么错** 频率检验的是"这段字符串常见吗"，而需要检验的是"这段字符串是不是一次真实引用"。**常见性与引用性正交**：`AG`、`12.5` 在语料里当然出现过不止一次。把弱判据当**许可证**，等于把"常见"当"正确"；而当**否决权**用，它是有价值的 —— 它的正确位置是**排除**，不是**准入**。

**怎么发现的** 自检全过之后做了**人工核对 20 条**（这一步是被要求加上的，很关键），一眼看出放行的都是评分列表。改成"段频只用于**拒绝** + 相对路径要求末段带已知扩展名 + 绝对路径看**存在性**"后，20/20 都是真实引用。
第二轮人工核对又抓到第二类问题：不是垃圾而是**标签错** —— 4/20 是把无协议头的主机前缀 URL 记进了"路径"类型，污染了类型拆分（路径 82.8%→81.1%、URL 65.9%→68.7%）。
（原始日志 #34（未随本仓库发布） §六）

**以后怎么避免** 用启发式前先问"它给的是允许还是禁止"：**弱判据只能当否决权，接受必须由强判据承担**（存在性、扩展名、可解析性、与外部对账）。自检通过不等于判据成立 —— 自检只能覆盖你想得到的情况；人工核对的样本要同时看两件事：**有没有垃圾**，与**有没有分对类**（"干净"的两种含义）。

## 七、抽取器的"看着对"与"它对"是两件事

**现象** 一个命令抽取器被真实输出**连续打脸三次**：
① 抽出的命令里 `cd` 出现 **503 次** —— 真实命令常写作 `cd X && 真命令`，抽取器把 `cd` 当成了命令本身；
② 40 多条**代码碎片**被当成命令（形如 `base64,{b64(f)}"}})`、`<字段>:{变量}`）—— 它在引号内部的 `;` 和 `|` 上切了段；
③ `ed = json.load(...)` 被抽成命令 `ed` —— 前一道长度闸门把很长的解释器路径丢掉后，切分循环**走进了 heredoc 体内部**。
（原始日志 #34（未随本仓库发布） §六）

**为什么错** 抽取器在"看起来对"的状态下照样产出一串整齐的数字，而下游每个结论都会继承它的错误。三次都不是解析目标有问题，是**抽取器没有被真实输出撞过** —— 与第三条同源：**"指标 / 抽取器看着对"与"它对"是两件事，而两者的差距只有一次抽样那么贵。**

**怎么发现的** 三次都是**把抽出来的前若干条产物逐条打印出来看**才发现的。这不是理论推演能替代的：写每一条规则的时候它都"有理由"。

**以后怎么避免** 抽取器写完先在真实数据上跑，并逐条看前 20–50 条产物；用"**不该出现的东西**"做断言（单独出现的 `cd`、含引号或括号的碎片、纯标识符、引号内的分隔符），而不只用"该出现的东西"做召回检查；改抽取器就重跑同一批样本，输出每个条目进出变化的差异对照；把"样本化的人工核对"写进流程，而不是等结论被质疑时才补。
（原始日志 #44（未随本仓库发布） 附 D4 第二版、"跨三次事故的共同教训"）

---

## 如果只记三句

1. **验证要落在"功能是否发生"上，不落在"是否挂上了"上**；反证不变红时，先怀疑用例而不是实现。
2. **任何新指标或新抽取器，先抽样看它抓到了什么，再相信它的数**；荒谬的比例、全 0、全 1 一律先当 bug。
3. **统计之前先定义总体**：数重了要去重，数了不该数的要按来源剔除 —— 去重救不了后者。
